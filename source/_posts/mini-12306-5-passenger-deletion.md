账号 A 名下有两个乘车人。编号 7 从没用来买过票，编号 8 出现在一张待支付订单里。A 用自己的会话依次删除：

```text
DELETE /api/passengers/7   → 204
DELETE /api/passengers/8   → 409
```

第二条返回“该乘车人已被订单引用，无法删除”。两条记录的主人是同一个账号，请求也来自同一个人。结果不同，原因不在权限，而在记录有没有进入过订单。

删除这个接口因此同时在处理两件事：清理一份资料，以及判断这份资料是否已经成为某笔交易的一部分。前者是一次业务选择，后者是一条历史关系；如果删除和下单同时发生，还要决定谁有最终裁决权。

## 1. 先确认记录属于当前账号

删除入口从会话取账号，路径只提供记录编号：

```java
@DeleteMapping("/{id}")
@ResponseStatus(HttpStatus.NO_CONTENT)
public void delete(
        @PathVariable Long id,
        HttpServletRequest httpRequest
) {
    Long userId = currentUserSession.requireUser(httpRequest).id();
    passengerService.delete(userId, id);
}
```

Service 接到两个值后，先按归属把记录查出来：

```java
@Transactional
public void delete(Long userId, Long passengerId) {
    // Check ownership first so foreign records look exactly like missing ones.
    findById(userId, passengerId);

    // Orders keep their own snapshot, but still reference this row.
    if(passengerMapper.countOrdersByPassengerId(passengerId) > 0) {
        throw new PassengerInUseException();
    }

    try {
        // The owner condition makes foreign rows impossible to delete.
        if(passengerMapper.deleteByIdAndUserId(passengerId, userId) != 1) {
            throw new PassengerNotFoundException();
        }
    } catch(DataIntegrityViolationException exception) {
        // A concurrent order may appear after the check; the foreign key blocks it.
        throw new PassengerInUseException();
    }
}
```

`findById` 使用 `WHERE id = ? AND user_id = ?`。记录不存在、属于别的账号，或者刚被删过一次，都会在这里得到 404“乘车人不存在”。订单检查排在它后面。

顺序不能换。假设先查订单引用：B 拿别人的编号逐个尝试，有订单的返回 409，没订单的返回 404。状态码的差别足以让 B 判断哪些编号存在。先按归属统一返回 404 后，B 只能知道这些编号在自己名下不可用，无法确认它们在别处是否存在。

这条归属查询是一条普通 SELECT，不加锁。它回答的是“这条记录现在归谁”，不是“这条记录在删除前不会被别人动”。事务给了它一个读快照，但快照只描述读的那一刻；真正的删除语句还要自己再带一次 `user_id`，原因在第三节。

路径参数不是数字时，请求在进入方法前就转换失败，返回 400；数字但查不到，才是业务层的 404。两者不在同一层处理。

## 2. “被订单引用”是一条历史记录

订单检查只有一句计数：

```java
@Select("""
        SELECT COUNT(*)
        FROM ticket_orders
        WHERE passenger_id = #{passengerId}
        """)
long countOrdersByPassengerId(@Param("passengerId") Long passengerId);
```

它没有状态条件，没有时间范围，也不区分购买模式。只要 `ticket_orders` 里还有一行指向这个乘车人，计数就大于零。已支付、待支付、已取消、已超时的订单都算；旧的数量订单、计价订单、座位订单，以及多人订单的每条明细，也都是 `ticket_orders` 行，都带着 `passenger_id`。

某个乘车人只要下过一单，这条资料就不能再通过这个接口删除，哪怕那笔订单后来取消了。取消、支付、超时改变的是订单状态，订单行仍留在 `ticket_orders` 里，`passenger_id` 仍指向这个乘车人。引用计数不看状态，结果还是 409。

当前项目没有删除订单的接口，业务代码里也没有删除订单的 SQL，订单不会从表里物理消失。如果以后新增了物理删除订单的路径，这条引用关系会跟着改变，需要重新定义规则；现在的删除接口不对这种情况负责。

为什么不只统计待支付和已支付？因为那样会让业务检查和数据库约束给出不同答案。一条已取消的订单仍在表里，`passenger_id` 仍指向这个乘车人，DELETE 到数据库时依然会被外键拒绝。业务检查说“可以删”，数据库说“不行”，最后还是要落到同一个冲突上，只是报错更晚。计数不加状态，是为了和外键实际覆盖的范围保持一致。

订单下单时已经保存了姓名和证件快照，为什么还要保留乘车人这一行？快照决定订单上显示什么，外键决定订单关系指向谁。`ticket_orders.passenger_id` 始终指向 `passengers.id`。删掉父行，只能让引用悬空、级联删除订单，或者把外键置空。第一种破坏历史，后两种改变“订单一定对应某个乘车人”的模型。当前实现没有选其中任何一种，而是拒绝删除。

如果没有外键，这张订单仍然能显示姓名和证件，看起来一切正常。但“这条订单对应哪一条乘车人资料”就没有答案了：以后要按乘车人查历史、核对身份、处理退款或改签，都找不到落点；同一个人重新添加一次，会得到一个新的 `passengers.id`，旧订单也不会自动指过去。快照保存的是成交时的文字，外键保存的是这条文字背后的记录。两者不是一回事。

订单中与乘车人有关的字段可以分成三块：

| 字段 | 作用 |
| --- | --- |
| `passenger_id` | 外键，指向 `passengers.id`，历史关系靠它定位 |
| `passenger_name`、`passenger_id_card` | 下单时的展示快照，不随资料修改而变 |
| `status` | 订单状态，不参与删除引用计数 |

V1 没有显式给 `passenger_id` 写索引，但 InnoDB 会为外键列自动建一个；引用计数和外键检查都走这个索引，不需要全表扫描。V10 又加了一个以 `user_id` 开头的复合索引，那是给活动行程防重和订单查询用的，不是为这条只按 `passenger_id` 过滤的计数准备的。

当前没有软删除。给 `passengers` 加一个 `deleted` 标记，看起来能保留行，但所有查询都要记得过滤，同账号证件唯一键也会阻止同一个人重新添加；它不是在这个接口里加一个字段就能顺带解决的问题。账号注销、订单删除和数据清理都需要各自的关系规则，不在本篇范围内。

## 3. 真正删除时仍然带着归属条件

业务检查通过后，DELETE 语句自己也限定 `id` 和 `user_id`：

```java
@Delete("""
        DELETE FROM passengers
        WHERE id = #{id}
          AND user_id = #{userId}
        """)
int deleteByIdAndUserId(
        @Param("id") Long id,
        @Param("userId") Long userId
);
```

影响行数不等于 1，Service 抛出 `PassengerNotFoundException`。前面已经查过归属，这里再带一次条件，是因为 `findById` 负责响应语义——先区分 404 和 409；DELETE 才是真正改数据的语句，不能靠“前面查过了”来保证安全。记录在两条语句之间被另一个会话删掉时，DELETE 同样影响 0 行，返回 404 也符合事实。

两个会话同时删除同一条记录时，也会走到这个分支。两条请求都先查到记录，都通过引用检查；第一条 DELETE 拿到行锁并删除，第二条在行锁上等待，等第一条提交后再执行，发现目标行已经不存在，影响 0 行，返回 404。一个 204、一个 404，没有 500，也没有第二条 DELETE 把已经删掉的行再删一次。

DELETE 的影响行数没有 UPDATE 那种歧义。UPDATE 把字段改成相同的值，影响行数可能是 0，也可能不是，取决于驱动按“改变行”还是“匹配行”计数；DELETE 删到就是一行，没删到就是没有。`CLIENT_FOUND_ROWS` 影响的是 UPDATE 的“匹配行”语义，不会把 DELETE 的 0 行变成 1 行。

删除成功返回 204，正文为空。现有用例在删除后查了详情、列表和 `passengers` 表：详情 404，列表只剩另一条记录，目标行在表里也确实不存在。行是物理删除的，不是被某个查询条件藏起来。

## 4. 检查通过之后，仍可能冒出一笔订单

`@Transactional` 把归属检查、订单计数和 DELETE 放进同一个事务。它保证这几步共享一个读视图，也保证写操作失败时没有别的写入需要撤销。但它不会在 `findById` 时锁住这条乘车人：两个普通 SELECT 读的是快照，DELETE 直到执行时才去拿行锁。所以事务并没有把“检查”和“删除”变成一个不可分割的动作；它只是让检查看到一致的状态，让删除自己承担最后的判断。

订单计数是普通 SELECT。MySQL 默认的可重复读下，它读取事务内第一次查询建立的快照，不加锁。另一个事务可以在计数返回 0 之后、DELETE 执行之前，为这个乘车人提交一笔新订单。

```text
时刻   删除事务 T1                          下单事务 T2
t1     findById：记录存在
t2     count：0
t3                                          INSERT ticket_orders(passenger_id = 9)
t4                                          COMMIT
t5     DELETE passengers WHERE id = 9 ...
t6     外键检查发现子记录，错误 1451
```

快照在 t1 的 `findById` 就建立了，t2 的计数沿用它。所以计数看不到 t3 才插入、t4 才提交的订单；即使把计数挪到 t4 之后，只要还在同一个事务里，读到的仍是 t1 时的数据。0 在当时是准确的，只是它描述的是快照，不是 t5 那一刻的表。

这个结论依赖隔离级别。如果事务跑在 READ COMMITTED 下，每条普通 SELECT 都会重新取快照，挪到 t4 之后的计数就可能看到新订单，提前返回 409。当前项目使用 MySQL 默认的可重复读，所以计数固定在 t1 的视图里；换隔离级别，检查的早晚会变，但 DELETE 的最终裁决不会变。

DELETE 则是当前读。它要找到并锁住目标行，读的是最新已提交的数据，不看 T1 的快照。InnoDB 在删除父行时会检查 `ticket_orders` 里有没有 `passenger_id = 9` 的子记录，这个检查同样面对当前数据。t4 提交的订单已经在表里，检查命中，语句以错误 1451 结束，父行没有被删掉。

外键检查本身也要拿锁。它扫描子记录时，会对看到的行加共享锁；如果碰到的是一条还没提交的插入，T1 必须等 T2 给出结果。T2 提交，T1 得到 1451；T2 回滚，子记录消失，删除继续。两种顺序都不会留下“父行没了、子记录还在”的状态，区别只在 T1 是立刻失败还是先等一会儿。等待超过 `innodb_lock_wait_timeout`（默认 50 秒）时，T1 会以锁等待超时结束；那不是完整性异常，也不会变成 409。

MySQL 返回错误 1451，Connector/J 抛出完整性约束异常，Spring 再翻译成 `DataIntegrityViolationException`。Service 的 catch 只包住 DELETE，把这个完整性异常换成 `PassengerInUseException`，全局异常处理再返回 409“该乘车人已被订单引用，无法删除”。catch 的范围是整个 `DataIntegrityViolationException`，不是精确到 1451；如果以后 `passengers` 上多出别的完整性约束，这里也会统一说成“已被订单引用”，那时需要按约束名或更窄的异常再细分。

这里的预检查并不承担最终裁决。它给出的 409 是正常路径上的快速回答，真正面对并发的是外键。两者的分工也可以反过来验证：去掉计数，预先存在订单的删除仍然会走到 DELETE，被外键拒绝后由 catch 转成同样的 409；去掉外键、只留计数，常见情况也照样通过。现有那条“有订单时删除返回 409”的用例先下单再删除，计数会在 DELETE 之前抛出 `PassengerInUseException`，所以它证明的是预检查这条路，而不是 catch 那条路——两种实现都能让它通过。要区分它们，得看 DELETE 有没有真的执行，或者临时去掉其中一个约束再跑一遍，而不是只看状态码。

时间线反过来，代价落在下单这一边。T1 先提交删除，T2 的 INSERT 在检查外键时找不到父行，MySQL 返回 1452（插入子行时父行不存在）。这个错误发生在订单事务内部，没有被任何 catch 接住：`@Transactional` 回滚整笔创建，已经扣掉的库存恢复，幂等预占也一起撤销，最后交给全局异常处理的是一个未预期的 500。客户端看到的是服务器错误，而不是 409；但数据仍然一致——乘车人已经删掉，订单没有建成，库存没有少。删除赢了，下单这一边承担了失败的代价。

两边都还没结束时，还有第三种可能：死锁。T1 的 DELETE 已经拿到父行的排他锁，外键检查要扫子索引；T2 的 INSERT 已经写入新子行，外键检查要拿父行的共享锁。T1 等 T2 的新子行，T2 等 T1 的父行，形成环。InnoDB 的死锁检测会选中一方回滚：如果 T1 被选中，删除以死锁错误结束，乘车人还在，客户端拿到 500；如果 T2 被选中，订单、库存和幂等一起回滚，乘车人已被删掉，客户端同样拿到 500。死锁异常和锁等待超时都属于 `PessimisticLockingFailureException` 的子类，不是 `DataIntegrityViolationException`，不会被那个 catch 转成 409。这个环是否出现，取决于索引、隔离级别和两条语句实际的加锁顺序；现有用例没有构造过，只能作为机制上的可能，而不是已观测到的结果。

那能不能在删除开始时就把乘车人行锁住，让下单的 INSERT 排队？可以，但这条锁必须被所有会写子记录的路径共同遵守才有意义。订单创建现在并不显式锁乘车人，它只在 INSERT 时通过外键拿父行的共享锁；删除方一旦持有排他锁，这条共享锁就会等待，窗口确实能关上。代价是删除从加锁那一刻到提交都占着这把锁，期间该乘车人的新订单全部阻塞；订单方此时还握着车次锁和库存行锁，等待会顺着锁链传下去，死锁的可能也不会消失，只是换了一个环。更重要的是，即使加了这把锁，外键仍然要保留——它约束的是所有写入者，而不只是这一条代码路径。当前实现选择不加这把锁，接受窗口存在，让外键做最终裁决。

事务由 Spring 代理生效：控制器拿到的是代理对象，方法进入时开启事务，正常返回后提交，异常抛出后回滚。这里还有一个容易忽略的默认规则：Spring 只在运行时异常和 `Error` 上回滚，受检异常默认提交。当前 `PassengerNotFoundException`、`PassengerInUseException` 以及 Spring 翻译出的完整性异常都是运行时异常，所以都会回滚；如果以后有人在这个方法里加了一个受检异常并指望回滚，需要显式写 `rollbackFor`。代理也有边界：如果 `delete` 是被同一个类里的另一个方法直接调用，走不到代理，事务不会开启；这里是控制器从外部调用，代理生效。

现有用例没有构造“删除与下单同时发生”的场景，catch 分支、1452、死锁和锁等待超时都没有专项运行证据；上面的过程来自外键约束和异常映射的机制推演。能确认的是：预先存在订单时，计数会先返回 409，DELETE 不会执行。

## 5. 被拒绝之后，订单和资料都保持原样

引用检查的用例先用真实下单流程创建一笔订单，再尝试删除乘车人。删除被拒绝后，订单详情仍返回 200，`passengerId` 还是那条记录，`passengerName` 是下单时保存的快照，状态仍是 `PENDING_PAYMENT`。乘车人记录逐字段不变，库存也停在下单后的数量。

拒绝没有留下半成品。订单显示姓名和证件时可以依赖自己的快照，不必再读乘车人表；但它的 `passenger_id` 仍指向那条记录。快照让历史订单不随资料修改而变，外键让这条历史关系始终有落点。

把删除和下单放在一起，结果可以列成一张表：

| 发生顺序 | 最终判断 | 删除请求 | 下单请求 | 数据结果 |
| --- | --- | --- | --- | --- |
| 订单已存在 | 计数 | 409 | 不受影响 | 订单、乘车人、库存不变 |
| 计数后订单提交 | 外键 1451 | 409 | 已成功 | 订单保留，乘车人保留 |
| 删除先提交 | 外键 1452 | 204 | 500，事务回滚 | 乘车人删除，订单、库存、幂等都不留下 |
| 锁等待成环或超时 | InnoDB | 可能 500 | 可能 500 | 被回滚的一方不留下半成品 |

第一行有用例；第二行只有机制推演；第三、四行没有用例。表里没有“删除成功、订单也成功”的组合——外键不允许它出现。

用例覆盖的是单边路径：删除成功 204、记录不存在 404、跨账号 404、重复删除 404、被订单引用 409、非数字 400、未登录 401。被引用那条用例在下单之后删除，计数已经大于零，DELETE 根本没有执行，所以它验证的是预检查，不是 catch。真正需要并发用例的是第二到第四行：两个会话、同一乘车人、一个删除一个下单，才能看到 1451、1452 或死锁。现有测试没有这样的门闩。

当前没有软删除，也没有级联删除。删除成功就是物理删除，有引用就拒绝。账号注销、订单删除和数据清理都不在这个接口的范围内，它们需要各自的关系规则，不能靠给 `passengers` 加一个 `deleted` 标记顺带解决。

## 资料可以删除，历史关系不能断

删除乘车人时，归属回答“这条记录是不是你的”，引用回答“它能不能消失”。前者让越权和不存在都停在 404，后者让有历史订单的记录停在 409。正常路径上，业务检查给出可读的结果；并发和遗漏时，外键保证不会留下断掉的引用。

但“谁说了算”和“谁拿到什么状态码”不是同一个问题。外键保证的是数据一致：不会同时留下一个被删掉的乘车人和一张指向它的订单。它不保证两边都得到 409——删除先成功，下单会以 500 结束；死锁时总有一边被回滚。409 是设计好的业务结果，500 是没被专门处理的竞态结果。两者都让数据停在一个可解释的状态，只是客户端的感受不同。

资料可以删除，但一旦进入过订单，它就不再只是资料。下一篇从一笔数量订单开始，看扣库存和写订单为什么必须一起成功。
